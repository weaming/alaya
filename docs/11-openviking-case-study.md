# 11 · 外部案例研究：OpenViking

> **本文性质**：外部系统的调研记录与经验输入，**不属于 Alaya 的设计文档**。
> 它不定义任何 Alaya 的接口、schema 或不变式；其中的"启示"是**待决策的外部输入**，
> 只有在被明确采纳后，才应写入 `07-evaluation.md` / `10-algorithmic-core.md` 等设计文档。
>
> 证据来源：`github.com/volcengine/OpenViking` 的 issues / PR / discussions / releases，
> 以及公开外部评测。所有数字均标注了条目编号，便于复核。
> 采集时间：2026-09-13。

---

## 0. 为什么研究它

OpenViking 与 Alaya 的问题域高度重叠（Agent 长期记忆、上下文分层、蒸馏、检索注入），
但它已经是一个**有真实用户、有 benchmark、有 3,700+ PR 的工业产品**，而 Alaya 仍在设计阶段。
因此它的**工程轨迹与踩坑清单**，是判断 Alaya 哪些设计能被验证、哪些会被现实打回的廉价信息来源。

本文件分两部分：

- **B 部分**：OpenViking 当前的重心是否已从"铺功能"转向"补质量"。
- **C 部分**：由以上证据提炼的、供 Alaya 决策的 7 条启示。

## 2. B 部分：当前重心已转向"补质量"

### 2.1 量化证据：最近 300 个 PR 的类型分布

对最近 300 个 PR 的标题前缀统计（`gh api .../pulls?sort=created`，取标题首词）：

| 类型 | 数量 | 占比 |
|---|---|---|
| **fix** | **183** | **61.0%** |
| feat | 48 | 16.0% |
| docs | 24 | 8.0% |
| test | 9 | 3.0% |
| refactor | 9 | 3.0% |
| perf | 8 | 2.7% |
| ci / build / revert / chore | 10 | 3.3% |
| 无标准前缀 | 9 | 3.0% |

> 结论：**每 6 个 PR 里有近 4 个是修 bug**，新功能占比不到 1/6。
> 这与"用新功能拉社区"的早期阶段是两种状态。

### 2.2 发布与提交节奏

- 版本：`v0.4.10`（07-16）→ `v0.4.19`（09-08），约 **1–2 周一个 patch 版本**；
  同期还并行发布 CLI / Python SDK / Go SDK 的独立版本（如 `cli@0.4.18`、`python-sdk@0.1.10`、`sdk/go/v0.0.2`）。
- 主分支近期提交（2026-09-09 ~ 09-13）几乎全部是 `fix(...)`，`feat` 稀疏且多为
  Studio/CLI 交互类小功能，而非核心记忆/存储能力。

### 2.3 近期修复的具体方向（示例）

| PR / issue | 方向 |
|---|---|
| #4979 `fix(vectordb): never score a record from bytes that are not its vector` | 向量索引读到未初始化内存，产生 ~1e37 的查询无关脏分（对应 #4377） |
| #4971 / #4970 | 删除快照会重建被删路径 / 留下空目录（存储层一致性） |
| #4965 | 重新引入 pgvector/OpenGauss 并给 qdrant import 加开关（见 2.4） |
| #4945 `fix(pathlock): atomically replace stale tokens during takeover` | 路径锁令牌接管竞态 |
| #4935 / #4932 / #4942 | ACL 子树分页、管理列表性能 |
| #4934 | AGFS 非目录错误应终止语义任务，而不是无限重试 |
| #4890 | 新增"记忆提取排障"技能（官方开始把踩坑做成运维文档） |

### 2.4 关键反转：被移除的开源向量后端正在回归

- 早期 PR **#3872** 移除了 Qdrant / OpenGauss 向量后端（PR 描述为空）。
- 社区在 discussion **#4067** 强烈反弹：*"基本上杀死了用户部署其他云的可能性……每家都有自己业务绑定的云，不可能都用火山"*，并指其造成事实上的**火山引擎锁定**。
- 2026-09-12 出现 **PR #4965**：`fix(pgvector): make OpenGaussIndex non-abstract + gate qdrant import`，
  把 pgvector/pgvector 后端带回可运行状态。

> 这是"质量/可迁移性"压过"产品策略"的一个直接信号。

### 2.5 B 部分结论

**是，重心已明显从"铺功能"转向"补质量与可运维性"。** 具体表现为：

1. PR 以 fix 为主（61%），patch 版本密集，核心能力迭代放缓；
2. 修复集中在**存储一致性、锁竞态、检索正确性、ACL、成本控制**——都是"让已有设计真正可靠"的工作；
3. 官方开始产出运维/排障类内容（#4890、成本跟踪帖 #744），并纠正早期激进的架构裁剪（#4965 回归 vector backend）；
4. 但**问题流入仍快于处理**（229 open，近期 open/closed ≈ 22/5），说明远未收敛。

对 Alaya 的含义：OpenViking 已经替我们**暴露并正在偿还**"可变 FS + 锁 + LLM 蒸馏"这条路的工程债。
Alaya 若走"只追加 + 内容寻址"，理论上可跳过其中一部分（如锁竞态、快照重建），
但**LLM 蒸馏侧的债无法通过换存储模型规避**（见 C 部分）。

## 3. 效果证据摘要（供 C 部分引用）

### 3.1 官方声明

| 指标 | 官方数字 |
|---|---|
| LoCoMo 用户记忆准确率 | 24–57% → 80–83%（三个 Agent 集成） |
| 输入 token | −34.3–91.0% |
| 查询延迟 | −58.45–66.10% |
| tau2-bench 成功率 | Retail +6.87pp、Airline +11.87pp |

外部能找到的评测文章（知乎 / InfoQ / CSDN / 掘金 / 火山开发者社区）**基本是官方博客的转载或改写**，
数字一致，独立复现极少。

### 3.2 唯一一次独立全量复现尝试：#1258（34 条评论，全仓最多）

| 阶段 | 事实 |
|---|---|
| 初始结果 | 全量 LoCoMo 1540 题 **118/1540 = 7.66%**（category 4 仅 6.78%） |
| 维护者归因 | 评测脚本把**整个 session 当一条 message 上传**（事件提取依赖 message 下标）+ 无 session 时间戳 → 事件记忆基本未生效 |
| 追加问题 | Python 3.14 **段错误崩溃**；评测脚本 API 不兼容（需回退 3.12） |
| 调参后 | 开 Memory V2 + `recallLimit=30`、`recallScoreThreshold=0.35`、`recallPreferAbstract=false`、`recallTokenBudget=10000` |
| 结果 | sample2：**~30% → 61.18%** |
| 维护者反应 | "这个准确率已经比我们 seed-code-2.0 的效果高了" |
| 结局 | 用户**未跑全量**，转而直接与 opencode 等工具结合使用 |

**结论**：官方 80–83% **未被外部完整复现**；结果对评测脚本、召回参数、模型选择极度敏感，默认配置基本不可用。

### 3.3 自托管报告：#4879（open，2026-09-09）

用户用 Ollama + `qwen2.5:7b` / `qwen2.5vl:3b` 自托管，结论：

- `extract_loop` 走 ReAct + 严格的 **Python-DSL 最终操作解析器**；
- `qwen2.5vl:3b` **不支持 tool calling**；
- `qwen2.5:7b` 本身 tool calling 正常，但经 server 的 litellm→ollama 路径**收不到工具定义**，回退到输出 fenced Python 文本，反复触发解析错误。

**结论**：**记忆提取实际上要求 Doubao 级别的云模型**；本地开源模型目前无法驱动核心能力。
这直接限制了"隐私优先、本地自托管"这一卖点的适用范围。

### 3.4 生产问题分类（详细清单）

- **成本失控**：#505（O(n²) 重处理，500 条记忆日耗数十万 embedding token + 2000+ 次 429，已修）、
  #3226（无上限 prompt，52k+ tokens）、#4963（300k+ token VLM prompt，open）、
  #1595（递归 VLM 可达上千万 token）、#531/#529（概览生成无预算保护，已修）、#744（官方成本跟踪帖）。
- **记忆质量**：#3006（照抄原文不蒸馏，74KB 技能定义成单条记忆 → "死记忆"，open）、
  #1549（用户空间实测 50/50 命中皆 L2，L0/L1 结构性不可达）、#1737（Reranker 被静默禁用，100% 回退）、
  #4413（行号前缀在合并记忆中累积）、#4205（跨 Workspace 注入噪声，open）、#4525（记忆有时存有时不存）。
- **性能稳定性**：#2120（S3 下 session commit P95 数十秒）、#4948（find 检索 ~31s）、
  #4515 / #4842 / #3274（插件热路径延迟与 CPU 打满）、#2489（段错误）、
  #4938 / #4943 / #4283（路径锁失效 / TOCTOU）。
- **安全隐私**：#4977（ACL 通过 grep/文本检索绕过泄漏，2026-09-13）、#4292（记忆内容提示注入）、
  #2899（密钥入记忆）；无内置 RBAC、无 SOC 2 / ISO 27001。

## 4. C 部分：对 Alaya 的 7 条启示（外部输入，待决策）

> 以下每一条都是**候选决策**，不是已确定的 Alaya 设计。采纳前应各自开一条
> "是否采纳 / 采纳到什么程度 / 落在哪个文档"的记录。

### C1 · 主战场在"语义边界"，不在代数内核

OpenViking 最持久、最难修的缺陷全部发生在**自然语言 → 结构化**这一步：
#3006（照抄不蒸馏）、#1549（原始对话入库）、#4879（本地模型无法驱动提取）。
而它的存储/锁/格式层相对可靠。
**对 Alaya**：`10-algorithmic-core.md` 只保证"输入符号之后"的确定性与可重放，
不解决边界层的质量。**归一化/蒸馏的质量与可评估性，权重应不低于代数内核。**

### C2 · 成本上限必须是设计的一等公民

O(n²) 重处理（#505）、无上限 prompt（#3226/#4963）、递归 VLM（#1595）说明
"蒸馏/摘要"会吃掉全部预算，且**官方宣称的 token 节省只发生在检索侧，超支发生在蒸馏侧**。
**对 Alaya**：金字塔蒸馏必须默认**增量 + 事件驱动 + 硬预算**；
`05-inference.md` 的调度与 `04-storage.md` 的写放大控制需要一条明确的**成本预算条款**。

### C3 · "派生层可重建"必须搭配"派生失败可见"

#1737：生产环境（38 用户）Reranker 因空文档被**静默禁用**，100% 回退到向量分而无人知晓。
**对 Alaya**：在"派生层永远不是真源"之外，应补一条不变式——
**任何派生索引的降级/回退必须显式上报，禁止静默降级**（否则"宁可搜不到"会退化成"悄悄搜错"）。

### C4 · scope/world 过滤是刚需，不是打分项

#4205 证明"全局记忆池 + 向量检索"必然导致跨项目注入污染。
**对 Alaya**：`world` 与 `scope` 的匹配应作为**硬过滤**（召回前置条件），
而不是 rerank 公式里的一个加权项。

### C5 · 记忆写入要可控、幂等、可确认

#4525"有时存有时不存"是 LLM 抽取式写入的固有病。
**对 Alaya**：显式 `POST /claims` + `claim_key` 幂等应作为**默认写入路径**，
而非对自动蒸馏的补充；自动蒸馏产出的只能是候选声称（与 `03-facts-and-consensus.md` 一致）。

### C6 · 多后端可迁移是生存问题

#4067 的反弹 + #4965 的回归说明：把真源/索引绑死到单一云会被社区抛弃。
**对 Alaya**：`04-storage.md` 的"内容寻址副本、无人拥有唯一正本"要落到
**至少一个开源、可迁移的检索/存储后端**上，并在文档里写成硬约束。

### C7 · 基准必须自证：评测脚本本身要受版本控制与公开复现

#1258 的核心教训是：**评测脚本 + 默认参数可以让结果相差近 10 倍**（7.66% → 61% → 官方 83%）。
**对 Alaya**：`07-evaluation.md` 的离线回放 harness 是对的方向，
但必须进一步要求——**评测脚本、数据切片、gold label、复现命令一并纳入版本控制并公开**，
否则"两月后零提示续上"这类验收仍会重蹈覆辙。
