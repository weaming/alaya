# 05 · 计算与推理

本层回答：**在这套存储之上，如何把数据变成事实、把事实变成知识、把知识变成行动判断。** 它由五台引擎与一个完整认知循环组成。

## 1. 完整认知循环

一切推理围绕一个闭环，它是"科学方法"的存储化：

```
Observe ──▶ Record ──▶ Claim ──▶ Verify ──▶ Believe ──▶ Act ──▶ Observe
  │(事件入基岩)       (quad声称)   (证据+共识+     (scope内     (影响世界)
  │                                 世界内自洽)     world_fact)
  └──────────── 新观测/反例回到入口，闭环永不停 ───────────────┘
```

**关键认识**：这个环在时间中持续自我修正；系统记忆的不是"P 为真"，而是"P 在一段时间内、某 world、某 scope、由谁基于什么证据认定为真"。经得起时间考验的不是任何一条事实，而是**事实被产生与修正的机制**。

## 2. 引擎一：事实裁决（Truth Engine）

### 2.1 置信度传播

在论证图（03 §2.1）上做约束传播：

```
conf(claim) = Σ w_e · conf(evidence) · independence(evidence)
            − Σ w_a · conf(attack)     − Σ w_u · conf(undercut)
            + w_c · consensusSupport(claim, scope)
            + w_k · charterConsistency(claim, world)
```

- 证据独立性是关键权重：两条互相引用的证据不算"多重独立"；
- 观察者可信度本身是修正中的记忆（历史准确率），形成二阶可信度；
- 结果是一个**可解释的得分卡**（哪些证据、哪些反例、哪些共识、哪些自洽贡献了多少），供裁决记录留痕。

### 2.2 触发式裁决

裁决不必每条都跑：只对状态可能翻转的声称触发（新证据到达 / 出现 attack / 共识达成 / 宪章变更）。用惰性 + 事件驱动，控制计算成本。

### 2.3 反事实与可计算 oracle

在可计算世界（代码库、虚拟世界、仿真模型）内，裁决可以主动检验：

- 代码世界：把声称转成测试/类型检查/运行——**"线上事故 → 测试复现 → 修复 → 测试通过"是同一裁决机的实例**；
- 虚拟世界：用宪章规则推演剧情/设定冲突，输出 canon 冲突报告；
- real 世界：预测 → 等待新观测验证（predictive check）。

**符合判据（consilience）**：同时被观测支持、又被独立模型复现的声称置信度最高。

## 3. 引擎二：共识计算（Consensus Engine）

### 3.1 加权聚合

同一 scope 内出现冲突时：

```
支持度(claim, scope) = Σ participant.weight(scope, topic) · stance / Σ weight
weight = 角色权重(权威canon层更高) × 历史准确率(可修正) × 时效衰减
```

**跨时距关联不可省略**。外部实测：冲突双方的时间距离从近（5–10 会话）拉远到远（20–25 会话）时，
各系统一致退化，且差距随距离单调扩大——说明仅靠局部 recency 与短程检索无法处理远期冲突
（[12 §6](12-academic-evidence-on-agent-memory.md)）。因此：

- 冲突检测不得只在相邻时间窗内进行，须维护**跨长时距的关联边**（同一 `subject+predicate` 的历史值链）；
- 共识聚合的输入应包含远期异议，而非只聚合近期活跃的声称；
- `supersedes` 链与 `applicableWhen` 条件链共同承担这一职能（03 §2.3、§4.2）。

### 3.2 共识协议（状态机）

```
conflict ──协商──▶ majority ──强化──▶ unanimous ──外推──▶ cross_scope
   │                  │
   └──── agree-to-disagree（异议入 dissent，永不删除）
```

- 协议目标不是消灭分歧，而是**达成可行动的 scope 内结论，同时完整保留异议**；
- 共识对象可被超越（supersedes），旧共识是历史；
- **跨 scope 收敛**：个人→家庭→共同体→…逐层一致则向上迭代；物理法则 = 全 scope 收敛的极限。小范围共识是"可落地的客观性"。

### 3.3 社会性事实 vs 自然事实

- 社会性事实（约定/规范/canon/共同历史）：主要由共识机确立；
- 自然事实（天气/代码行为/物理事件）：主要由观测 + 可检验确立，共识只作佐证；
- 裁决记录必须标注事实类型，避免用错判据。

## 4. 引擎三：世界内推演（World Simulator）

- **世界状态**：每个 world 维护可计算的当前状态（real：事实快照；代码：代码库+依赖；虚构：canon 时间线与设定）；
- **推演**：给定状态 + 宪章规则 + 假设，生成"如果…则…"的事件（realm=virtual/fiction），写入基岩作为派生事件流，供裁决比对；
- **canon 冲突检测**：新设定与旧 canon 矛盾时，推演器产出冲突报告（哪条宪章、哪个旧设定、何种矛盾），交给共识机仲裁（作者声明 / 粉丝共识 / 平行世界分叉）；
- 世界状态本身是派生物（可从基岩重放重建）——**replayability** 是虚拟世界与代码世界的核心能力（代码世界即 CI/测试的意义）。

## 5. 引擎四：蒸馏与反思（Consolidation）

### 5.1 蒸馏管道

```
基岩事件批 → 蒸馏器(schema化抽取) → 候选声称(带证据) → 论证图待裁决
episodic 摘要 → 语义条目(semantic) → 核心画像(core, identity)
```

- 调度：任务/会话边界小蒸馏 + 定时深度蒸馏 + **空闲期 compute**（sleep-time reflection）；
- 蒸馏输出必须带证据引用与 importance/confidence 初值；
- **模型换代可重跑**：同一基岩用更好模型重蒸馏，记忆只变好不锁死。

### 5.2 遗忘调度（在派生层执行）

```
retention_score = importance × recency(最后命中) × scope活跃度
  高 ──▶ 自动注入槽
  中 ──▶ 仅可检索（不出现在 recall）
  低/过期 ──▶ archived（派生层删除/降冷，基岩永存）
```

### 5.3 核心画像（core）的特殊地位

core 是"人格同一性"的载体：用户价值观、铁律、长期偏好、跨年主线。它必须：

- 体积最小、质量最高（任何一次注入都常驻）；
- 变更最谨慎：core 更新需要更高共识阈值（如 dyad scope 一致同意），且 supersede 链完整保留（"你以前认为…，现在认为…"是关系记忆的一部分）。

### 5.4 状态推断（State Inference）

03 §2.3 定义了 `applicableWhen` 与 `dormant`，但只剩一个空位：**当所有相关声称都 dormant，
或从未被陈述过时，当前值是什么？** 这是"检索正确、信念错误"的根源，必须显式推断而非留给检索排序。

```
输入：StateVar 当前取值（来自事件流） + 宪章声明的依赖关系 + 存量声称
输出：inferred 声称（带推断依据与置信） 或  unknown（触发弃答）
```

**三条路径，按优先级降级**：

| 路径 | 条件 | 性质 |
|---|---|---|
| ① 符号推演 | 宪章声明了状态变量间的依赖（如 `#engagement_style` 依赖 `#role`） | 确定性、可重放，走符号内核（10 §3.6） |
| ② 条件检索 | 宪章未声明依赖，但存在 `applicableWhen` 匹配当前状态的声称 | 确定性命中，置信随条件匹配强度衰减 |
| ③ 边界侧推断 | 无法符号化的情形 | 走 LLM 边界，**产出候选声称而非结论**，进入论证图待裁决 |

**三条硬约束**：

1. **推断必须落为声称**，带 `attributedBy: pipeline:inference`、依据引用与置信，进入论证图与其他声称竞争——
   不允许只存在于单次响应的上下文里（否则不可审计、不可重放、不可被后续证据修正）；
2. **推断不得覆盖 `expressed` 声称**。它不是"更正"，只是多一条来源不同的声称；
   当两者冲突时，由事实裁决机按常规机制处理（谁更可信、条件是否匹配）；
3. **推断失败必须输出 `unknown` 并触发弃答**，不得用默认值或"最近值"填充。
   既有系统最典型的失败正是把 `dormant` 当成当前值（[12 §4.1](12-academic-evidence-on-agent-memory.md)）。

**触发**：状态变量变更时（新事件落基岩），标记依赖它的声称重新求值。事件驱动，不是每轮轮询。

**与检索的关系**：注入装配的优先级为 `operative` > `inferred` > `dormant`（见 §6.2）。
`dormant` 声称可以按需检索（用于回答"我以前怎么看"），但不参与自动注入。

**能力边界（诚实声明）**：路径 ① 要求宪章显式声明依赖，覆盖不到的世界（多数虚构世界、开放话题）
只能走 ②/③，可靠性显著下降。这与 10 §5 的能力边界一致——**不假装推断，推不出就弃答**。

## 6. 检索与注入（Recall，面向单次效率）

### 6.1 预算分配（硬上限）

| 槽位 | 预算（示例） |
|---|---|
| core（当前 scope 画像，含状态推断结果） | ~600 token |
| 话题相关 semantic/procedural | ~800 token |
| 相关虚构世界 canon 提示 | ~300 token（命中时） |
| 上限 | 硬顶，防止记忆吃光窗口 |

### 6.2 混合召回 + 重排

- 召回：向量语义 + 关键词/实体（人名、日期、专名、设定词）并集；
- 过滤：`world` 与 `scope` 必须匹配当前上下文（跨世界内容只能经映射边进入）；
- **适用性分层**：按 `operative` > `inferred` > `dormant` 分层（§5.4），`operative` 优先占位；
- 重排：`score = w1·语义 + w2·适用性 + w3·importance + w4·共识度 + w5·recency − w6·age`；
- 注入格式：改写为陈述句干条 + `(记于 …)` 时效标注 + 世界标签 + **适用性标注**。

**`recency` 的权重不得高于 `适用性`。** 这是本设计中最容易犯、后果最严重的一个排序错误：
"最近被陈述的值"恰恰是状态推断问题里**错误**的那个值（§5.4）。
排序若以 recency 为主，系统会稳定地、可复现地选中过时值，且检索指标看起来完全正常。

**冲突并置时的呈现规则**。外部实测（[12 §4.2](12-academic-evidence-on-agent-memory.md)）显示：
把新旧值不加标记地并列，模型会取平均、追问或挑旧的。因此：

- 同一 `subject+predicate` 的多条声称同时注入时，**必须显式标注哪条是当前适用值**、哪条是历史值；
- 条件化的值须连同**适用条件**一起注入（"在做 IC 时偏好 X；任 CEO 后偏好 Y"），而不是只给一个值——
  去掉条件线索正是"缩短历史反而更差"的原因；
- 冲突记忆的注入是**有损**的：宁可少注入，不可无标注地并列。

### 6.3 自动 vs 按需

- 自动注入负责"不该问的都知道"（高概率需要、低体积）；
- Search 工具负责"问了才知道的"（低概率、高体积）——**决策依据是预判概率，不是内容好坏**。

## 7. 引擎五（推理层的第五台）：跨世界桥推理

跨世界不做自由联想，只走显式映射边（02 §6）：

- **结构投影**：把世界 A 的关系结构投影到世界 B 作假设推演（"这段感情像《命运石之门》的哪条世界线"→ 用该结构给用户现实处境一个可讨论的模型）；
- **隐喻索引**：虚构世界的设定作为理解现实的模板（用户意义系统的高密度入口）；
- **跨世界事实不允许直接互相 attack**；类比只产生候选假设，必须回到各自 world 的判据验证；
- 代码世界 ⇄ 现实：事故（real）→ 复现（virtual 测试）→ 修复 → 上线（real）是同一个桥的标准动作。

## 8. 推理成本控制

### 8.1 调度原则

- 裁决惰性触发；蒸馏批量调度（非每回合）；
- 重蒸馏/全量重建放空闲期，带优先级队列；
- 可解释优先：每次裁决/共识输出得分卡，供审计与调试，避免黑箱传播错误；
- 所有 LLM 参与的步骤都产生"推理痕迹"（prompt 摘要 + schema 版本）写入基岩——**推理本身也是记忆**，未来更好模型可复核旧推理。

### 8.2 成本预算（硬条款）

外部实测：不同记忆架构的**每正确答案能耗跨度超过 47×**（4.1 kJ ~ 186 kJ）；
构造侧能耗可超过 300 次查询的全部查询能耗之和；agentic 架构的构造 token 成本随规模**超线性**增长
（某系统在 256K tokens 之后急剧发散）。原文结论是"长期成本由算法增长斜率而非初始 footprint 决定"
（[12 §5](12-academic-evidence-on-agent-memory.md)）。

定性调度不足以约束这条曲线，因此设硬预算：

| 条款 | 内容 |
|---|---|
| 单次蒸馏上限 | 每批事件的 token / 调用数 / 墙钟硬上限；超限则截断**并记录**，不静默降级 |
| 重放预算 | 单次重蒸馏的总量上限；超出则排队到下一空闲窗口 |
| **成本斜率监控** | 持续跟踪"每单位新增事件的蒸馏成本"；**该值持续上升即告警**——这是超线性增长的前兆信号，比总量告警更早 |
| 降级路径 | 预算耗尽时的优先级：core 与 operative 声称 > 近期事件 > 历史归档 |

**构造与查询的划分是本设计中最大的成本杠杆**：查询量高、历史稳定 → 把工作搬进构造（预先蒸馏）；
查询量低、持续摄入 → 保持轻构造。这条划分应是可配置策略，不是写死的架构常量。

**读宽度换写深度**：外部证据显示检索条目更多会帮助 QA 但**损害 agentic 决策**
（注意力从任务上下文转向检索块）。因此 §6.1 的注入预算是硬顶，不应为"召回更多"而放宽；
预算应优先投给写入侧的蒸馏与结构化。
